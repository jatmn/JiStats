## Background / What Happened

The original plan `.kilo/plans/1777163365512-quick-island.md` specified adding **additional** Codex throughput metrics (tokens/minute, prompts/minute) on top of existing subscription tracking. The implementation in commit `d2cbd00` followed the plan:

1. Added `CodexTokenUsageSnapshot` parsing in `OpenAIAdapter`
2. Imported snapshots into `usage_events` with `source_type = 'codex_local_rollout'`
3. Computed throughput in `AnalysisQueryEngine` by querying those persisted events
4. Surfaced results in `AnalysisPresenter`

### The Bug

The `codex_local_rollout` events were written into `usage_events`, but **existing subscription/usage queries did not filter them out**. This caused the new throughput data to leak into and distort existing metrics:

- Subscription usage counts included Codex token events
- Recovery/backfill comparisons counted them as local evidence
- Hourly/daily rollups included them in `requestCount`, `totalTokens`, and provenance counters
- Raw and hybrid aggregate queries treated them as billable usage

### The "Fix" (commit `095c1a9`)

Instead of isolating the Codex data at query boundaries, the programmer **reverted the persistence layer**:

- Removed the `AppController` import block entirely
- Removed `disableCodexTokenImportForTesting`
- Changed `AnalysisQueryEngine` to read directly from rollout files (bypassing `usage_events`)
- Added defensive `source_type != 'codex_local_rollout'` filters across ~10 queries

This made the symptom go away by removing the data source, but it **did not correctly implement the plan**. The throughput metrics now work, but:
- The `usage_events` table is no longer a historical store for Codex token usage
- Deduplication across refresh cycles is lost (file-scan is repeated every time)
- The metric glossary and progress docs still falsely claim persistence into `usage_events`
- Defensive `source_type != 'codex_local_rollout'` filters guard against data that can no longer be inserted

## Root Cause

The original implementation wrote telemetry-like events (`codex_local_rollout`) into the same table as subscription usage events without establishing a **query-boundary contract**. Every usage query that computes subscription metrics, rollups, backfills, or aggregates must explicitly scope to the source types it intends to include. The fix addressed this at the wrong layer (data ingestion instead of query scoping).

## Correct Fix Strategy

The right approach is **query-boundary isolation**, not ingestion removal. Codex token snapshots should be persisted (they are local telemetry, not subscription usage), and every subscription-scoped query should explicitly filter them out.

### Option A: Restore Persistence + Fix Query Boundaries (Recommended)

1. **Restore `AppController` import block** (revert the removal in `095c1a9`)
2. **Restore `disableCodexTokenImportForTesting`**
3. **Keep the existing defensive filters** (`source_type != 'codex_local_rollout'`) — they are now correct and necessary
4. **Revert `AnalysisQueryEngine` back to querying `usage_events`** for throughput instead of re-scanning files on every analysis build
5. **Update `StorageService::rebuildUsageRollups`** — the filter is already present and correct
6. **Update test expectations** in `test_storage_usage_rollups.cpp` — the test that inserts `codex_local_rollout` should either (a) expect it to be excluded from rollups, or (b) be moved to a dedicated throughput test
7. **Update docs** — `metric-glossary.md` and `progress.md` are actually *correct* about the intended architecture; the code just needs to match them

### Option B: Keep Direct File Reads + Drop Dead Code

If the decision is made that file-scan on every analysis build is acceptable (it re-scans up to 100 files, bounded by 3 days / 1000 snapshots), then the cleanup path is:

1. **Remove all dead `source_type != 'codex_local_rollout'` filters** from queries that no longer need them
2. **Remove the `codex_local_rollout` test fixture** from `test_storage_usage_rollups.cpp` or repurpose it
3. **Update `docs/metric-glossary.md`** to state the true source: local rollout files, not `usage_events`
4. **Update `docs/progress.md`** to state the true source
5. **Accept the tradeoff**: no historical deduplication, no cross-session persistence, repeated disk I/O on every analysis refresh

## Tradeoffs

| Concern | Option A (Restore Persistence) | Option B (Keep File Reads) |
|---------|-------------------------------|---------------------------|
| Historical tracking | Yes — events survive across sessions | No — only current local files |
| Deduplication | Yes — `insertUsageEvents` handles it | No — re-imports every time |
| Disk I/O per analysis | One indexed SQL query | File system scan (up to 100 files) |
| Correctness with plan | Matches original plan | Contradicts original plan |
| Doc truthfulness | Docs are already correct | Docs must be changed |
| Code cleanliness | Defensive filters are justified | Dead filters must be removed |
| Test stability | Test using `codex_local_rollout` is meaningful | Test should be removed or changed |

## Decision

**Option A is selected.** Codex throughput snapshots shall be persisted into `usage_events` with `source_type = 'codex_local_rollout'`. Subscription-scoped queries must explicitly exclude them. Throughput computation shall read from `usage_events` (not re-scan files). This keeps throughput as an **additional** metric alongside subscription tracking, not merged into it.

## Risks

1. **Missed query risk:** If any subscription-scoped query was missed in the filter audit, restoring the import will re-introduce the bug. Mitigation: the audit above is comprehensive — every `usage_events` query in `src/app/AppController.cpp`, `src/db/StorageService.cpp`, and `src/reporting/AnalysisQueryEngine.cpp` was checked. The missing ones are listed explicitly.
2. **Test expectation drift:** `test_storage_usage_rollups.cpp` currently has counts adjusted downward to match the no-import state. Restoring the import will change those counts again unless the test is updated to expect exclusion.
3. **Performance:** The original import runs on every `importEnabledLocalProviderActivity()` call, but deduplication in `insertUsageEvents` prevents duplicate rows. This is the same behavior as before `095c1a9`.
