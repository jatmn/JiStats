# Plan: Codex Application Throughput Metrics

> Superseded status: this was the original feature plan. Use
> `1777171278493-nimble-star.md` as the active corrective/consolidated plan.
> The original intent remains valid: Codex throughput is additive local
> telemetry and must not replace or contaminate subscription/quota metrics.

## Goal

Investigate and implement capture of Codex desktop-application usage throughput metrics:
- **Tokens per minute** (input + output token velocity)
- **Prompts per minute** (approximated by `token_count` event frequency)

## Feasibility Assessment

**Yes — this is feasible from existing local Codex artifacts without new API integrations.**

Codex already writes `token_count` events to local rollout JSONL files at:
- `%USERPROFILE%\.codex\sessions\**\rollout-*.jsonl`

Each event carries:
- `timestamp` (ISO 8601, per-event)
- `info.total_token_usage` / `info.last_token_usage` with:
  - `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`
- `rate_limits` (already parsed today for quota mirroring)

By comparing successive `token_count` events, JiStats can derive:
1. **Token delta** = `total_tokens₂ − total_tokens₁`
2. **Time delta** = `timestamp₂ − timestamp₁` (in seconds)
3. **Tokens per minute** = `(token_delta / time_delta) * 60`
4. **Prompts per minute** = `1 / time_delta * 60` (each `token_count` event ≈ one prompt/turn)

## Confidence And Limitations

| Concern | Reality |
|---------|---------|
| Real-time fidelity | Limited by Codex's own event-logging cadence (per prompt/turn, not per second). This gives accurate *per-prompt* throughput, not sub-second granularity. |
| Multi-session boundaries | If the user has multiple Codex sessions, each session writes its own rollout file. JiStats must either aggregate across all session files or pick the most active session. |
| Gaps / null `rate_limits` | Some builds emit `token_count` with `rate_limits: null`; the token `info` may still be present. The parser should ingest token counts even when rate-limit data is missing. |
| Provider exactness | This is **local-first estimation**, not provider-exact truth. Confidence tier should be `LocalExact` or `Estimated` depending on how much inference is required. |

## Proposed Implementation Path

### Phase 1: Parse and Persist Token Usage Snapshots

**Scope:** Extend the existing Codex rollout parser to extract `total_token_usage` and persist it.

1. **Extend `OpenAIAdapter` parser**
   - In `OpenAIAdapter::parseCodexRateLimitFixtureFile` (or a new companion method), also extract `payload.info.total_token_usage` fields when present.
   - Create a lightweight `CodexTokenUsageSnapshot` struct holding: `eventTime`, `inputTokens`, `outputTokens`, `totalTokens`, `sourcePath`.

2. **Collect across all rollout files**
   - Add `OpenAIAdapter::collectCodexTokenUsageSnapshots(directoryPath)` → `std::vector<CodexTokenUsageSnapshot>`.
   - Sort by `eventTime` ascending.

3. **Persist into `usage_events`**
   - Map each snapshot to a `UsageEvent` with:
     - `eventTime` = snapshot timestamp
     - `modelKey` = inferred from session context or left as `"codex"`
     - `requestType` = `"codex_turn"`
     - `inputTokens`, `outputTokens`, `totalTokens`
     - `sourceType` = `"codex_local_rollout"`
   - Write through `StorageService` into `usage_events` table (schema already supports these columns).
   - Deduplicate on `(eventTime, sourcePath)` to avoid re-importing the same event on every refresh.

### Phase 2: Compute Throughput in the Analytics Engine

**Scope:** Derive rolling tokens/minute and prompts/minute without schema changes.

1. **Add computed throughput queries**
   - In `AnalyticsEngine` (or `AnalysisQueryEngine`), add:
     - `computeTokensPerMinute(windowSeconds)` — queries `usage_events` for `sourceType = 'codex_local_rollout'`, computes deltas between consecutive events in the window, averages the rate.
     - `computePromptsPerMinute(windowSeconds)` — counts events in the window divided by window span.
   - Windows: 5 minutes, 30 minutes, 5 hours (aligned with existing activity windows).

2. **Confidence labeling**
   - Return `LocalExact` when deltas come from contiguous events in the same session file.
   - Return `Estimated` when aggregating across multiple sessions or when large gaps exist.

### Phase 3: Surface in Dashboard / Taskbar

**Scope:** Display throughput metrics without violating the existing metric-glossary deferred list.

1. **Dashboard Analysis workspace**
   - Add "Codex Throughput" section in `AnalysisPresenter` showing:
     - Current session tokens/minute (5-minute window)
     - Current session prompts/minute (5-minute window)
     - Trend sparkline over the last 30 minutes
   - Label with `Local` or `Estimated` badge.

2. **Taskbar (optional, scoped)**
   - The metric glossary explicitly defers "standalone taskbar RPM/TPM rate-limit gauges."
   - **Recommendation:** Do NOT add to taskbar for v1.0. Keep throughput as an Analysis-workspace feature only, or add it behind a user setting that is off by default.

### Phase 4: Validation

1. **Fixture tests**
   - Add synthetic rollout JSONL with multiple `token_count` events at known intervals and known token counts.
   - Assert computed tokens/minute and prompts/minute match expected values.

2. **Integration tests**
   - Run against real local `.codex/sessions/` if available on the machine.
   - Verify deduplication works across repeated refreshes.

## Alternatives Considered

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| Parse rollout files (proposed) | Passive, local-first, no new credentials, uses existing artifact | Cadence limited to Codex event logging; multi-session aggregation needed | **Recommended** |
| Codex app-server `account/rateLimits/read` JSON-RPC | Likely fresher | Requires live app-server integration, more moving parts | Future path only |
| Windows ETW / process I/O observation | OS-level, works even if Codex changes file format | Gives activity intensity, not exact token counts; invasive | Not recommended for exact tokens/prompts |
| OpenAI API platform usage endpoints | Provider-exact | Blocked by scope (`api.usage.read`); subscription users may not have API billing | Deferred advanced path |

## No-Go Boundaries

- Do NOT invent token counts when rollout files lack `info.total_token_usage`.
- Do NOT treat local throughput as provider-exact quota truth.
- Do NOT add throughput to the taskbar unless the user explicitly overrides the current v1.0 deferred metric list.
- Do NOT require new credentials, network calls, or OS-level hooks.

## Exit Criteria

- [ ] `OpenAIAdapter` extracts and persists `total_token_usage` from local rollout files into `usage_events`
- [ ] `AnalyticsEngine` / `AnalysisQueryEngine` computes tokens/minute and prompts/minute for 5m/30m/5h windows
- [ ] Dashboard Analysis workspace shows Codex throughput with appropriate confidence badges
- [ ] Fixture tests validate rate computation against known synthetic data
- [ ] `docs/metric-glossary.md` updated if new surface labels are introduced
- [ ] `docs/progress.md` updated with completion status

## Questions For The User

1. **Scope priority:** Should I implement both tokens/minute *and* prompts/minute, or start with just one? Tokens/minute is more informative; prompts/minute is simpler to compute.
2. **Surface preference:** Should throughput appear only in the Analysis workspace, or do you also want it surfaced in the main dashboard or taskbar? The metric glossary currently defers taskbar rate gauges.
3. **Multi-session behavior:** If you have multiple Codex sessions running, should throughput aggregate across all sessions or show only the most active one? Aggregating is easier but may overcount; per-session is more accurate but more complex to display.

## Risks

1. **Codex schema drift** — future Codex builds may remove `info.total_token_usage`. Mitigation: parser should degrade gracefully (skip token ingestion, keep existing rate-limit parsing).
2. **Multi-session overcounting** — aggregating across multiple simultaneous sessions could inflate rates. Mitigation: default to per-session rates or label cross-session aggregates as `Estimated`.
3. **Performance** — scanning all rollout files on every refresh could be expensive if the user has many sessions. Mitigation: leverage the existing watcher/backoff logic (already in `AppController` for Codex refresh) and only re-scan when file mtimes change.
